## 走查验证的良好点

1. **增量字段写入**（`stripUnchanged` + PATCH 只校验本次字段）：两台电脑各改各的不会互相覆盖，服务端也不拿全量校验拒掉历史脏数据
2. **账号唯一性双端兜底**：客户端切换时关同池其他，服务端 `markCurrent` 再强制一次；删当前自动顺延（`ensureCurrent`）
3. **失败一律回滚重拉**：保存/勾选/移动/置顶/切号失败都重新拉库，不存在「界面成功、库里没有」
4. **孤儿列机制**：任务所在电脑缺失时兜底成「未识别电脑」，任务永不丢；且该列不允许拖入
5. **搜索态语义明确**：只换电脑、不落顺序，并明确提示
6. 测试面扎实：5 套件 298 项 + e2e + 11 体检 + 变异测试 11/11，改前改后逐项一致

## 结论三问

1. **链路逻辑通顺吗？** 主干（任务/账号/置顶/拖拽）通顺；**旁支（电脑改名/删除对账号与 GitHub 的联动）不通** → P-01/P-02
2. **是补丁叠补丁吗？** 不严重：账号唯一性、孤儿列都有单点归属；但「电脑身份」有三个副本（machines 名、accounts 所属电脑、github 电脑），改名只有服务端在搬两个，客户端与筛选第三个没跟上 —— **P-01/P-02/P-03/P-04 都是同一根因：电脑身份没有单点归属**
3. **会无法操作/出 bug 吗？** P-01 会让人「找不到记录」；P-02 会让人误以为账号丢失；P-03 会让任务暂时「消失」——都能靠刷新恢复，但都违背「界面 = 真相」

## 建议处理（按风险分）

1. **P-01 + P-02（必修，同一个改法）**：改名/删机成功后，顺手 `loadAccounts()` + 若 `ghFilter.machine` 等于旧名则清空；3 行内改动，配 `audit_account_edit` 加一条断言
2. **P-04（建议修）**：GitHub「电脑」筛选的下拉改为「machines ∪ 记录里的电脑」，改名后仍能筛到历史记录（或改名时同步重写记录里的电脑，需产品定口径）
3. **P-03（建议修）**：改名先把旧名/旧任务快照存起来，失败时回滚内存（或改为「先写库、成功后再改内存」）
4. **P-05（文案）**：确认框改成「任务保留原电脑名，会出现在『未识别电脑』列；之后新建同名电脑会自动归位」
