# 维护指南

> 这份文档回答一个问题：**改了东西之后，我该动哪里？**
> 只讲维护链路，用法见 [README.md](README.md)。

---

## 一、最重要的一件事：资料库版 HTML 是生成物

`agent-workbench-资料库版.html` **不要手改**。它是拼出来的：

```
public/index.html   ──┐
                      ├─► 注入「离线快照层」──► 注入「CSV 数据源层」──► 资料库版 HTML
server.mjs SCHEMAS ───┘                                              └─► 4 个 CSV 模板
package.json version ─┘
```

**改了 `public/index.html` 或 `server.mjs`，必须重新生成**，否则资料包会悄悄过期——
界面是新的、字段是旧的，而且不报错。

### 重新生成

```bash
node library/tools/build.mjs
```

一条命令，HTML 和 4 个 CSV 模板一起更新。字段清单**从 `server.mjs` 的 SCHEMAS 派生**，
不硬编码——主项目加字段，CSV 模板自动跟着变，不用手改。

### 校验有没有漂

```bash
node library/tools/check.mjs
```

比对这些地方对同一件事的说法是否一致：

| 检查项 | 抓的是什么 |
|---|---|
| CSV 表头 ↔ SCHEMAS | 模板漏列 / 多列 |
| **HTML 内嵌字段 ↔ SCHEMAS** | **主项目改了没重跑 build（最常见的过期）** |
| HTML 版本号 ↔ package.json | 版本没跟上 |
| README / 提示词的枚举 ↔ SCHEMAS | 枚举漂移 |
| 提示词的数据形状 ↔ CSV 表头 | 文档和模板对不上 |

漂移了会报错并指出修法。退出码非 0，可以接进 CI。

> 这三个脚本本身也做过反向验证：故意删一列、改错枚举、多写派生字段，都能抓到。
> 不是"恒绿"的摆设。

## 二、改了什么 → 要动哪里

| 你改了 | 要同步 |
|---|---|
| `public/index.html`（界面 / 交互） | 重跑 `build.mjs` |
| `server.mjs` 的 SCHEMAS（加/删/改字段） | 重跑 `build.mjs`；检查 `数据字典.md`；CSV 模板会自动跟着变 |
| `package.json` 版本号 | 重跑 `build.mjs` |
| 批量导入的格式 / 字段规范 | 改 `public/index.html` 里的卡片规范 → 重跑 `build.mjs`；同步 `示例导入文本.md` |
| CSV 导入导出的行为 | 改 `library/tools/build.mjs` 里的 CSV 层 → 重跑 |
| 接数据源的步骤有任何变化 | 改 `接数据源提示词.md` |
| 资料包本身有版本性变更 | 记一笔到 `CHANGELOG.md` |

**加字段的完整清单**（最容易漏）：

1. `server.mjs` SCHEMAS 里加
2. 重跑 `build.mjs`（CSV 模板自动带上）
3. `数据字典.md` 补一行说明
4. 如果是枚举，`README.md` 的字段口径表补上
5. 跑 `check.mjs` 确认各处对齐
6. `CHANGELOG.md` 记一笔

## 三、两个脚本

| 脚本 | 作用 | 何时跑 |
|---|---|---|
| `library/tools/build.mjs` | 生成 HTML + 4 个 CSV 模板 | 改了主项目之后 |
| `library/tools/check.mjs` | 校验各处字段/枚举是否对齐 | 改完随时跑，或接 CI |

两个都是零依赖 Node 脚本，Node 18+ 即可。

`build.mjs` 从 `server.mjs` 抠 SCHEMAS 时用括号配对 + 求值——因为 `server.mjs`
顶层会启动 HTTP 服务，不能直接 `import`。如果以后 SCHEMAS 的写法变了导致抠不出来，
脚本会直接报错说找不到，不会静默生成错的东西。

## 四、谁是谁（别改错文件）

| 文件 | 性质 | 能手改吗 |
|---|---|---|
| `public/index.html` | **真源**（主项目界面） | ✅ |
| `server.mjs` | **真源**（字段与校验） | ✅ |
| `library/tools/build.mjs` | 生成脚本 | ✅ |
| `library/tools/check.mjs` | 校验脚本 | ✅ |
| `library/agent-workbench-资料库版.html` | **生成物** | ❌ 重跑 build |
| `library/awb-*.csv` | **生成物**（空模板） | ❌ 重跑 build |
| `library/README.md` | 用法文档 | ✅ |
| `library/数据字典.md` | 字段说明 | ✅ |
| `library/接数据源提示词.md` | 给 WorkBuddy 的提示词 | ✅ |
| `library/示例导入文本.md` | 示例 | ✅ |
| `library/CHANGELOG.md` | 资料包版本记录 | ✅ |

⚠️ 用户导出的 CSV（带数据的 `awb-*.csv`）不要提交进仓库——那是个人数据。
仓库里的 4 个是**空模板**，只有表头。建议 `.gitignore` 里排除用户导出目录。

## 五、派生字段：一个反复踩的坑

`machines` 表的 **`WorkBuddy账号` / `TRAE账号` 是派生只读值**，
由 `accounts` 表里「当前=true」的那条算出，存储里不留第二份。

所以：

- CSV 里**没有**这两列
- 接资料库表格时**不要**给它们建列
- 改登录态要去 accounts 表切「当前」，不是直接写机器表

这个项目在账号语义上栽过一次（把 WB/TRAE 登录账号当成同步记录的 GitHub 账号填，
服务端不校验就静默写脏了）。任何涉及账号的改动都先确认清楚是哪一类账号：

| 账号类型 | 用在哪 |
|---|---|
| WorkBuddy / TRAE 登录账号 | 机器登录态（派生） |
| GitHub 账号 | 同步记录的「账号」列（库里多是 `Simiely` 这种） |

## 六、发布

资料包变更后：

1. 跑 `build.mjs` + `check.mjs`
2. 更新 `CHANGELOG.md`
3. 提交（资料包的改动和主项目代码放同一个提交即可，它们是一体的）
4. 发 release 时附上 `agent-workbench-library.zip`

`agent-workbench-library.zip` 的内容 = `library/` 整个目录，用
`zip -r agent-workbench-library.zip library/` 打包。
